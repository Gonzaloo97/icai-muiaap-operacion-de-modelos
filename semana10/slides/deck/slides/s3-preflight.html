¿Qué pregunta el navegador antes?

1

El navegador pregunta con un preflight.

OPTIONS /v1/predictions
Origin: http://localhost:8501
Access-Control-Request-Headers: x-api-key

2

La API responde qué origen y cabeceras admite.

Access-Control-Allow-Origin: http://localhost:8501
Access-Control-Allow-Headers: x-api-key

3

Si encaja, envía la petición real.

POST /v1/predictions
X-API-Key: TU_API_KEY

20

Secuencia del preflight (6 min). Una petición con una cabecera no estándar como X-API-Key, o con Content-Type: application/json, no es «simple», así que el navegador pregunta antes con OPTIONS. Envía Origin (quién soy) y Access-Control-Request-Headers (qué cabeceras quiero mandar). Si la API responde con Access-Control-Allow-Origin igual a ese origen y permite las cabeceras, el navegador envía el POST real; si no, la petición real ni se envía y en la consola del navegador aparece un error de CORS. Detalle importante: el preflight no lleva la API key, así que CORSMiddleware lo responde antes de que actúen las dependencias de autenticación. Por eso CORSMiddleware se añade como middleware y no como dependencia. Demo (paso 4): curl -i -X OPTIONS http://127.0.0.1:8000/v1/scores -H "Origin: http://localhost:8501" -H "Access-Control-Request-Method: POST" -H "Access-Control-Request-Headers: x-api-key". Repetir con Origin: https://evil.example y comprobar que falta Access-Control-Allow-Origin.
