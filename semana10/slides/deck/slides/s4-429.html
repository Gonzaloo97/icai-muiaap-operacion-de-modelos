class FixedWindowLimiter:
    def __init__(self, limit: int, window: float = 60.0, clock=time.monotonic):
        self.limit, self.window, self.clock = limit, window, clock
        self.windows: dict[str, tuple[float, int]] = {}

    def hit(self, key: str) -> float | None:
        now = self.clock()
        start, count = self.windows.get(key, (now, 0))
        if now - start >= self.window:
            start, count = now, 0
        if count >= self.limit:
            return self.window - (now - start)
        self.windows[key] = (start, count + 1)
        return None

Fragmento literal de examples/limits_demo.py (4 min). windows guarda, por clave de cliente, cuándo empezó su ventana y cuántas peticiones lleva. hit devuelve None si la petición cabe, o los segundos que faltan para que se abra la ventana siguiente. La ruta convierte ese número en un 429 con Retry-After redondeado hacia arriba (math.ceil): con 41,2 segundos se envía 42, porque Retry-After es un entero y redondear hacia abajo invitaría a reintentar demasiado pronto. ¿Por qué clock=time.monotonic inyectable? time.time puede saltar hacia atrás si se ajusta el reloj del sistema; monotonic no. Y en los tests paso un reloj falso que avanzo a mano: así compruebo que la ventana se reinicia sin esperar 60 segundos reales (S10.4). Pregunta: ¿qué pasa con este diccionario si la API corre en cuatro procesos? Cada proceso tiene el suyo y el límite real se multiplica por cuatro; por eso en producción se usa Redis o el gateway. En la práctica la clase se llama FixedWindowRateLimiter y devuelve un RateLimitDecision con allowed, remaining y retry_after.
