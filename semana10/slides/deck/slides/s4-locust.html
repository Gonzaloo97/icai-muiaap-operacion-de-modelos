class DemoUser(HttpUser):
    wait_time = between(0.5, 2)

    def on_start(self) -> None:
        self.client.headers["X-API-Key"] = os.environ["LOCUST_API_KEY"]

    @task(8)
    def score(self) -> None:
        self.client.post("/v1/scores", json={"age": 42, "income": 38000})

    @task(1)
    def health(self) -> None:
        self.client.get("/health")

Fragmento literal de examples/locustfile.py (3 min). Locust simula usuarios con código Python: cada DemoUser espera entre 0,5 y 2 segundos entre tareas, pone su API key al empezar (leída de LOCUST_API_KEY, nunca escrita en el fichero) y elige tareas según su peso: 8 de cada 9 veces predice y 1 de cada 9 consulta /health. Tres métricas que voy a pedir en el informe: RPS (throughput), p50 y p95 (la mediana y el percentil 95 de la latencia; el p95 es lo que sufre el usuario con peor suerte de cada veinte) y el porcentaje de fallos, donde cuentan los 429. Pregunta: si veo un 30 % de 429, ¿la API va mal? No necesariamente: el limitador está haciendo su trabajo; la conclusión depende del límite configurado frente a la carga simulada. Aviso: una prueba en el portátil mide el portátil; sirve para comparar antes y después, no para dimensionar producción. En la demo (paso 6): uv run --group load locust -f examples/locustfile.py --headless -u 20 -r 5 -t 1m --host http://127.0.0.1:8000.
