Rate limiting (4 min). ¿Por qué limitar? Un modelo cuesta CPU, GPU o dinero por llamada; sin límite, un cliente con un bucle mal escrito tumba el servicio para todos. Se limita por cliente autenticado, no por IP: detrás de una IP puede haber una oficina entera. Ventana fija: cuento peticiones en bloques de 60 s; problema: 60 al final de un bloque y 60 al principio del siguiente son 120 en pocos segundos. Ventana deslizante: cuento las de los últimos 60 s exactos; más justo, más memoria. Token bucket: cada cliente tiene un cubo de fichas que se rellena a ritmo constante; permite ráfagas cortas sin superar la media; es lo que usan muchos gateways. En la práctica usamos ventana fija en memoria del proceso: suficiente para aprender, pero con dos réplicas cada una cuenta por su lado; en producción el contador vive en Redis o el límite lo pone el API gateway. La respuesta: 429 con el sobre de S9, code rate_limited, y Retry-After con los segundos enteros que faltan; las respuestas permitidas llevan X-RateLimit-Limit y X-RateLimit-Remaining. El texto exacto del message lo fija el código.
